# Тачкиоск

Маркетплейс объявлений о продаже машин. REST API: продавцы выкладывают объявления,
покупатели смотрят ленту, администратор видит все объявления и снимает лишние.

Проект вырос из Garage: сначала консольное приложение на коллекциях, потом REST API учёта машин
на Spring Boot (тег `v2.0-rest`). Теперь машина — это объявление с продавцом, ценой, городом
и статусом. Старые машины миграция V8 перенесла в архивные объявления.

## Что умеет

- Продавец регистрируется, создаёт черновик, правит его и публикует. Для публикации нужны цена
  и город. Опубликованное отмечает проданным или снимает в архив, из архива публикует снова.
- Покупатель без входа смотрит ленту опубликованных: поиск по словам из марки, модели и описания,
  фильтры по марке, году, цене, пробегу, городу и характеристикам, сортировка, страницы или курсор.
  Цену опубликованного или проданного объявления можно получить в другой валюте по курсу ЦБ.
- Свои объявления всех статусов продавец видит в `/api/me/listings`. Чужие черновики и архив
  не видны никому, кроме администратора.
- Администратор видит все объявления с логином продавца и может снять любое опубликованное в архив.
- Публикация уходит событием в Kafka. Его читают две группы потребителей, уведомления и аналитика,
  пока они только пишут в лог.

## Стек

Java 21, Spring Boot 4.1, Spring Security, Hibernate 7, PostgreSQL 16, Flyway, Kafka (KRaft),
Redis 7, springdoc-openapi, Micrometer + Prometheus, JUnit 6, Mockito, Testcontainers,
Docker compose, GitHub Actions.

## Запуск

Нужен Docker с памятью от 3 ГБ.

```bash
cp .env.example .env
```

В `.env` заполнить `DB_PASSWORD`, `JWT_SECRET` и `ADMIN_PASSWORD`. Секрет не короче 32 символов:

```bash
openssl rand -base64 48
```

```bash
docker compose up -d --build
```

Первая сборка идёт внутри Docker и занимает несколько минут.

| Что | Адрес |
|---|---|
| API | http://localhost:8080 |
| Swagger | http://localhost:8080/swagger-ui.html |
| Prometheus | http://localhost:9090 |
| kafka-ui | http://localhost:8090 |
| Postgres | localhost:5433 |

## Авторизация

Администратора приложение создаёт при старте из `ADMIN_USERNAME` и `ADMIN_PASSWORD`.
Поменял пароль в `.env` и перезапустил: пароль обновится. Без них приложение не стартует.
Если такой логин уже занят обычным пользователем, приложение не стартует и пароль ему не перезаписывает.

Остальные регистрируются сами: логин 3–32 символа из строчных латинских букв, цифр и `_`,
пароль от 8 символов и не длиннее 72 байт в UTF-8.

```bash
curl -X POST localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"<логин>","password":"<пароль>"}'
```

Токен из ответа передаётся в заголовке `Authorization: Bearer <токен>`. Живёт 30 минут.
Читать опубликованные объявления может любой. Создавать объявления может любой вошедший,
продавцом становится владелец токена.
На вход 5 попыток в минуту с одного адреса. Шестая получит 429.

## API

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| POST | `/auth/register` | все | регистрация, роль всегда USER, 201 |
| POST | `/auth/login` | все | токен |
| GET | `/api/listings` | все | лента опубликованных с фильтрами, см. «Поиск в ленте» |
| GET | `/api/listings/feed` | все | та же лента по курсору, без номера страницы и total, см. «Лента по курсору» |
| GET | `/api/listings/{id}` | все | объявление. Черновик и архив видят только продавец и ADMIN |
| POST | `/api/listings` | вошедший | черновик, 201 и `Location` |
| PUT | `/api/listings/{id}` | продавец | изменить: все поля и `version` из последнего GET |
| POST | `/api/listings/{id}/publish` | продавец | опубликовать: нужны цена и город |
| POST | `/api/listings/{id}/sold` | продавец | отметить проданным |
| POST | `/api/listings/{id}/archive` | продавец или ADMIN | снять в архив |
| DELETE | `/api/listings/{id}` | продавец | удалить черновик, 204. Опубликованное не удаляется, его снимают в архив |
| GET | `/api/me` | вошедший | id, логин и роль: берутся из принципала, который фильтр уже загрузил, второго запроса нет |
| GET | `/api/me/listings?status=` | вошедший | свои объявления всех статусов, по умолчанию сначала новые |
| GET | `/api/admin/listings?status=` | ADMIN | все объявления любых статусов с логином продавца, по умолчанию сначала новые |
| GET | `/api/listings/stats` | все | по опубликованным: количество, средняя мощность, самая мощная модель |
| GET | `/api/listings/{id}/price?currency=USD` | все | цена по курсу ЦБ, только для опубликованных и проданных |

Топливо, коробка и кузов необязательны, значения из списков:

| Поле | Значения |
|---|---|
| `fuelType` | `PETROL`, `DIESEL`, `HYBRID`, `ELECTRIC`, `GAS` |
| `transmission` | `MANUAL`, `AUTOMATIC`, `ROBOT`, `CVT` |
| `bodyType` | `SEDAN`, `HATCHBACK`, `WAGON`, `SUV`, `COUPE`, `CONVERTIBLE`, `MINIVAN`, `PICKUP` |

Значение не из списка даёт 400 с перечнем допустимых. Номер вместо имени (`"fuelType": 1`) тоже 400:
иначе порядок констант стал бы частью API. Тот же список стоит CHECK-ом в базе.

Статусы объявления и переходы. Всё, чего нет в таблице, запрещено и даёт 409.

| Из | В | Действие |
|---|---|---|
| `DRAFT` | `ACTIVE` | publish |
| `ARCHIVED` | `ACTIVE` | publish, повторная публикация с новой датой |
| `ACTIVE` | `SOLD` | sold, проданное больше не меняется |
| `ACTIVE` | `ARCHIVED` | archive |

Порядок проверок при изменении: нет объявления или оно не видно — 404, видно, но не твоё — 403,
переход запрещён или не хватает цены и города — 409. ADMIN может снять объявление в архив,
но не публикует и не продаёт за продавца.

### Поиск в ленте

Все фильтры необязательные и складываются через И. Границы «от» и «до» включаются.

| Параметр | Что ищет |
|---|---|
| `q` | слова из марки, модели и описания, до 200 символов, см. «Поиск по словам» |
| `brand`, `model`, `city` | точное совпадение без учёта регистра, пустая строка не фильтрует |
| `yearFrom`, `yearTo` | год выпуска |
| `priceFrom`, `priceTo` | цена в рублях, не больше 10 знаков до запятой и 2 после |
| `mileageTo` | пробег не больше, км |
| `fuelType`, `transmission`, `bodyType` | значение из списка выше |

```
GET /api/listings?brand=toyota&yearFrom=1990&yearTo=2005&priceTo=5000000&transmission=MANUAL
```

«От» больше «до» — 400 с причиной. Не тот тип (`?yearFrom=abc`) — 400 «Поле yearFrom: неверный формат»,
присланное значение в ответ не попадает.

### Поиск по словам

`q` ищет по марке, модели и описанию с учётом словоформ: `?q=небольшой пробег` найдёт «с небольшим пробегом».
Работает вместе с остальными фильтрами. Синтаксис как у поисковиков: `"зимняя резина"` — слова подряд,
`резина -дтп` — без слова, `подарок or обмен` — любое из двух. Незакрытые кавычки и скобки не ошибка.

Без `sort` сначала самые подходящие: совпадение в марке и модели весит больше, чем в описании,
при равенстве — новые. С `sort` порядок от клиента. Лента по курсору с `q` идёт по дате.

Слова приводятся к основе стеммером, а не по словарю: «дизель» и «дизельный» — разные основы
(`дизел` и `дизельн`), беглую гласную он не знает («владелец» и «владельца»), «бмв» не найдёт BMW.
Запрос из одних стоп-слов («и», «на») ничего не находит.

### Лента по курсору

`GET /api/listings/feed?size=20` отдаёт `items` и `nextCursor`. Следующую страницу берут с `&cursor=<nextCursor>`,
фильтры те же, что у ленты. `nextCursor = null` — дальше объявлений нет. Порядок один: сначала новые.

Курсор хранит время публикации и id последнего объявления на странице, следующая начинается строго после него.
Новые объявления не сдвигают уже отданные страницы: на ленте по номеру страницы последнее объявление первой
страницы после вставки приезжает и на вторую, курсор такого не допускает. Глубина не важна: страница после
100 000 объявлений читается за то же время, что первая. Неверный курсор или `size` не от 1 до 100 — 400.

Пагинация: `?page=0&size=20&sort=price,asc`. Больше 100 на страницу не отдаётся.
Сортировать можно по `publishedAt`, `createdAt`, `price`, `year`, `mileageKm`, `horsePower`, `id`,
по остальному 400. По умолчанию сначала новые. К любой сортировке добавляется `id`,
чтобы при равных значениях строки не прыгали между страницами.

Все ошибки приходят в одном формате:

```json
{
  "timestamp": "2026-09-24T19:12:35",
  "status": 404,
  "error": "Not Found",
  "message": "Объявление с id: 99 не найдено",
  "path": "/api/listings/99"
}
```

400 ошибка в запросе, 401 нет токена, 403 не хватает прав, 404 нет объявления или пути,
405 и 415 не тот метод или формат, 409 конфликт со статусом объявления, 429 лимит входа,
503 не ответил ЦБ.
500 только если ошибка у нас.

## Как устроено

- Сущности не выходят из сервиса. Наружу только DTO на `record`.
- Схему базы ведёт Flyway (V1–V13). Hibernate её только проверяет (`ddl-auto: validate`).
- V8 переименовала `cars` в `listings` с сохранением id и данных. Старые машины стали архивными
  объявлениями технического продавца `garage-legacy`, под ним нельзя войти. Цена 0 стала NULL.
  Это проверяет `MigrationOnLegacyDataTest`: накатывает V1–V7, кладёт старые данные, потом V8.
- Пароли в BCrypt. Он учитывает только первые 72 байта, а `@Size` считает символы: кириллическая
  буква занимает 2 байта, поэтому длина в байтах проверяется отдельно, до обращения к базе и BCrypt.
- Регистрация: `existsByUsername` отсекает обычный случай, а две одновременные регистрации одного логина
  ловит UNIQUE в базе. Вторая получает 409, а не 500. Тест запускает такие пары в двух потоках.
- Админка защищена в два уровня: правило `/api/admin/**` в `SecurityConfig` и `@PreAuthorize`
  на методе сервиса. Если одно забудут на новом эндпоинте, второе всё равно не пустит.
- Админский список подтягивает продавцов тем же запросом через `@EntityGraph`. Страница из 10
  объявлений от разных продавцов: 2 SQL (страница и count) против 12 без графа. Считается
  в `PostgresRepositoryTest` через Hibernate Statistics.
- Объявления равны по id: одна строка, загруженная в двух persistence context, — одно объявление,
  новое без id равно только себе. Хэш один на класс, иначе после save объявление терялось бы
  в `HashSet`. Тип проверяется через `instanceof`: прокси Hibernate — наследник `Listing`, сравнение
  с ним не грузит строку и не падает, даже если сессия прокси уже закрыта.
- Кто что видит и меняет, решает `ListingAccessPolicy`, одна на все действия. Чужой черновик отдаёт
  404, а не 403: по коду ответа не должно быть видно, что объявление есть. Политика в базу не ходит
  и получает уже загруженные данные, поэтому одинаково работает с карточкой из кэша и из базы.
- Время в объявлении ставится из `Clock`, поэтому в тестах оно фиксированное.
- Публикация отправляет событие в топик `listing-published`, его читают группы `notifications`
  и `analytics`. Сервис про Kafka не знает: он публикует событие Spring, в Kafka его отправляет
  `ListingEventsRelay` после коммита (`@TransactionalEventListener(AFTER_COMMIT)`). Откаченная
  публикация ничего не отправляет. Подтверждение от Kafka не ждём, ошибку отправки считает
  `listings_events_failed_total`. Это at-most-once: если приложение упадёт между коммитом
  и отправкой, событие потеряется. Надёжное решение — transactional outbox.
- Нулевой символ (`\u0000`, `%00`) в любой строке запроса — 400. Postgres не принимает его в тексте,
  и раньше такая строка доходила до SQL и давала 500. Строки в JSON проверяет `NoNulStringsModule`,
  query-параметры — `NoNulParametersAdvice`.
- Отказ в правах из сервиса отдаёт 403, а не 500: `AccessDeniedException` ловит свой обработчик.
  Если токена нет, 401.
- Кэш-прокси стоит снаружи транзакционного (`@EnableCaching(order = LOWEST_PRECEDENCE - 1)`),
  поэтому карточка выкидывается из кэша уже после коммита, а не до него. Узкая гонка остаётся:
  GET прочитал строку до коммита и положил её в кэш после сброса. Её ограничивает TTL в 10 минут.
- PUT принимает `version` из последнего GET. Если объявление успели изменить, 409 с актуальной версией:
  две открытые формы не затирают друг друга. `@Version` в сущности ловит только пересекающиеся
  транзакции, а правки с разницей в минуты ловит сравнение версии клиента. Одновременные изменения
  одного объявления получают 409, а не 500.
- У опубликованного объявления нельзя убрать цену или город, проданное не редактируется.
- Объявление по id кэшируется в Redis на 10 минут. В кэше карточка без учёта того, кто смотрит,
  права проверяются после кэша. Без Redis приложение работает дальше: кэш просто промахивается,
  а лимит входа не действует.
- Запись в кэш синхронная (`immediateWrites`). Spring Data Redis 4 по умолчанию пишет асинхронно:
  сразу после удаления GET иногда отдавал удалённую машину из кэша. Тесты кэша падали
  примерно в каждом четвёртом прогоне.
- Курс берётся с зеркала ЦБ `cbr-xml-daily.ru`. Таймауты 3 с на подключение и 5 с на чтение.
  Если ЦБ не ответил, клиент получит 503.
- Статистика считается агрегатами в SQL.
- Фильтры ленты собираются из `Specification` через `Specification.allOf`. Пустой фильтр отдаёт
  `Specification.unrestricted()` и не добавляет условия. Статус `ACTIVE` стоит в фильтре всегда.
  Поля берутся из метамодели `Listing_`, её генерирует `hibernate-processor` при сборке:
  опечатка в имени поля ломает компиляцию, а не запрос в рантайме.
- Лента и поиск по марке идут по частичным индексам `(published_at desc, id desc)` и
  `(upper(brand), published_at desc, id desc)` с условием `status = 'ACTIVE'`: страница читается
  из индекса в нужном порядке и останавливается на 20-й строке. Фильтр по марке строит
  `upper(brand) = upper(?)`, поэтому в индексе то же выражение, а не просто `brand`.
- Индексы создаются и удаляются с `CONCURRENTLY`, чтобы не останавливать работу с таблицей.
  Для этого блокировка Flyway сессионная (`spring.flyway.postgresql.transactional-lock: false`),
  иначе миграция зависает.
- Поиск по словам — полнотекстовый поиск Postgres. `search_vector` — generated column (V12):
  `to_tsvector('russian', …)` от марки и модели с весом A и от описания с весом B. Postgres пересчитывает
  его при каждом INSERT и UPDATE, сущность колонку не маппит. По ней частичный GIN (V13).
  Условие `search_vector @@ websearch_to_tsquery('russian', ?)` и `ts_rank` для порядка собираются в той же
  `Specification`, что и остальные фильтры: функции регистрирует `FullTextFunctions` (Hibernate
  `FunctionContributor`), а немаппленную колонку подставляет встроенная `SqlColumn` с алиасом таблицы.
- Деньги в `BigDecimal`. Округление один раз в конце.

## Производительность

`perf/` — миллион объявлений через `generate_series`, запросы ленты в том виде, в каком их строит Hibernate,
и замеры `EXPLAIN (ANALYZE, BUFFERS)`. Как повторить и полная таблица — в `perf/README.md`.

Индексы под ленту — частичные, только по опубликованным (V10). Postgres 16 в Docker, медиана из 10 прогонов:

| Запрос | Страница до → после | count до → после |
|---|---|---|
| лента без фильтров | 225 → 0,19 мс | 107 → 61 мс |
| марка | 138 → 0,19 мс | 237 → 162 мс |
| марка + год + цена | 132 → 1,1 мс | 130 → 166 мс |
| город + кузов | 129 → 11 мс | 123 → 138 мс |
| страница 5000 (`offset 100000`) | 531 → 298 мс | — |
| та же позиция по курсору (`/feed`) | 0,15 мс | не нужен |

Страница теперь читается из индекса без сортировки, а основное время ответа уходит на `count`:
индексом его почти не ускорить. Лента по курсору `count` не делает и не зависит от глубины.

Поиск по словам (`?q=`, GIN из V13) против `ILIKE '%…%'` на тех же данных:

| Запрос | Страница | count |
|---|---|---|
| редкая фраза, 1 373 совпадения | 5,9 мс (ILIKE 45 мс) | 3,8 мс (ILIKE 857 мс) |
| частая фраза, 105 тысяч совпадений, по релевантности | 406 мс | 311 мс (ILIKE 860 мс) |
| частая фраза по дате (`/feed?q=`) | 0,56 мс | не нужен |

Частая фраза по релевантности медленная: `ts_rank` нужен каждой найденной строке, и запрос читает почти
всю таблицу. Хранимый вектор увеличил таблицу с 308 до 512 МБ. Подробности — в `perf/README.md`.

## Метрики

`/actuator/prometheus` собирает Prometheus раз в 15 секунд.

| Метрика | Что считает |
|---|---|
| `listings_added_total` | созданные объявления. Не `listings_created`: Prometheus-клиент отрезает суффикс `_created` у счётчиков |
| `listings_published_total` | публикации |
| `listings_events_failed_total` | события о публикации, которые не ушли в Kafka |

| `cache_gets_total{cache="listings"}` | попадания и промахи кэша |

## Тесты

```bash
./mvnw verify
```

Нужен запущенный Docker: часть тестов поднимает контейнеры через Testcontainers.
319 тестов: unit на Mockito, контроллер через `@WebMvcTest` с настоящей безопасностью, клиент ЦБ
на встроенном `HttpServer`, репозитории и миграции на настоящем Postgres, полный контекст
с Postgres, Kafka и Redis. Контейнеры полного контекста поднимаются один раз на весь прогон.
CI гоняет их на каждый push в `main` и на каждый PR.

## Postman

`postman/Tachkiosk.postman_collection.json` проходит сценарий целиком: регистрация продавца
и покупателя, черновик, правка с версией, публикация, лента, поиск по словам и карточка без входа, цена в долларах,
продажа, удаление черновика, архив от админа. Кроме удачных ответов проверяются отказы:
чужой черновик — 404, чужое опубликованное — 403, устаревшая версия и повторная публикация — 409,
админка без токена — 401.

Продавец и покупатель регистрируются заново на каждый прогон. Перед запуском заполнить
в переменных коллекции `adminUsername` и `adminPassword` из `.env`. Запускать целиком через Run
или из консоли:

```bash
npx newman run postman/Tachkiosk.postman_collection.json \
  --env-var adminUsername=admin --env-var adminPassword=<пароль>
```

В сценарии 3 входа, а лимит 5 в минуту с одного адреса: повторный прогон — через минуту.

## Структура

```
com.example
├── controller   REST без логики
├── service      бизнес-логика, транзакции, кэш, события
├── repository   Spring Data JPA
├── model        сущности
├── dto          record и маппер
├── exception    свои исключения и общий обработчик
├── security     JWT фильтр и конфиг
├── client       клиент ЦБ
├── config       Kafka, кэш, Swagger
├── event        событие для Kafka
├── listener     слушатели Kafka
└── ratelimit    лимит входа на Redis
```
