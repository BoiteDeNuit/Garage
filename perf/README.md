# Замеры ленты

Как быстро отвечает `GET /api/listings` на миллионе объявлений и что меняют индексы.
Поиск по словам (`?q=`) — в конце, в разделе «Поиск по словам».

## Как повторить

1. Поднять приложение, как в разделе «Запуск» основного README (`docker compose up -d --build`).
   При старте Flyway прогонит миграции, сид пишет в уже готовую схему.
2. Залить миллион объявлений (около 40 секунд). Скрипт откажется работать, если в `listings` уже больше 1000 строк:
   ```bash
   docker exec -i databaseGarage psql -U garage -d garage < perf/seed.sql
   ```
3. Для поиска по словам залить описания (около 40 секунд до V12, больше минуты после):
   ```bash
   docker exec -i databaseGarage psql -U garage -d garage < perf/seed_text.sql
   ```
4. Снять планы:
   ```bash
   docker exec -i databaseGarage psql -U garage -d garage < perf/queries.sql
   ```

В `queries.sql` запросы ровно в том виде, в каком их строит Hibernate (снято через `show-sql`),
только параметры подставлены литералами. На каждую страницу Spring Data делает два запроса:
саму страницу и `count` для `totalElements`, поэтому замерены оба.

## Данные

`seed.sql` детерминирован (`setseed`), поэтому замеры повторяются.

| Что | Сколько |
|---|---|
| объявлений | 1 000 000: ACTIVE 699 754, SOLD 99 607, ARCHIVED 100 192, DRAFT 100 447 |
| продавцов | 500 |
| марок, моделей, городов | 15, 45, 20. Марки неравномерные: Lada чаще всего, Toyota — 75 тысяч активных |
| размер таблицы с индексами | 238 МБ до V10, 296 МБ после |

## Где мерил

Postgres 16.15 в Docker с настройками по умолчанию (`shared_buffers` 128 МБ, `work_mem` 4 МБ,
2 параллельных воркера), 4 ядра. Каждый запрос — 10 прогонов после одного прогревочного, в таблице медиана
`Execution Time` из `EXPLAIN (ANALYZE, BUFFERS)`.

## До индексов

Из индексов только первичный ключ, `idx_listings_seller` и `idx_listings_brand_upper` по `UPPER(brand)`.

| Запрос | Страница | План страницы | count | План count |
|---|---|---|---|---|
| лента без фильтров | 225 мс | Parallel Seq Scan → Sort | 107 мс | Parallel Seq Scan |
| марка | 138 мс | Bitmap Index Scan по `UPPER(brand)` → Sort | 237 мс | Bitmap Heap Scan |
| марка + год + цена | 132 мс | Bitmap Index Scan по `UPPER(brand)` → Sort | 130 мс | Bitmap Heap Scan |
| город + кузов | 129 мс | Parallel Seq Scan → Sort | 123 мс | Parallel Seq Scan |
| лента, страница 5000 (`offset 100000`) | 531 мс | Parallel Seq Scan → Sort | — | — |

Что видно:
- Лента читает всю таблицу и сортирует 700 тысяч опубликованных, чтобы отдать 20 строк.
  Индекса под `published_at desc, id desc` нет.
- Индекс по марке находит 75 тысяч Toyota, но их всё равно приходится читать из таблицы и сортировать.
- `count` на каждую страницу стоит столько же, сколько сама страница: это половина времени ответа.
- Глубокая страница самая медленная: `offset` не пропускает строки, а сортирует и выбрасывает первые 100 000.

## После индексов (V10, V11)

| Индекс | Колонки | Условие | Размер |
|---|---|---|---|
| `idx_listings_feed` | `published_at desc, id desc` | `status = 'ACTIVE'` | 28 МБ |
| `idx_listings_brand_feed` | `upper(brand), published_at desc, id desc` | `status = 'ACTIVE'` | 36 МБ |

Индекс `UPPER(brand)` из V6 удалён в V11: марку ищут только в ленте, её закрывает `idx_listings_brand_feed`.

| Запрос | Страница до | Страница после | count до | count после |
|---|---|---|---|---|
| лента без фильтров | 225 мс | 0,19 мс, Index Scan по `idx_listings_feed` | 107 мс | 61 мс, Index Only Scan |
| марка | 138 мс | 0,19 мс, Index Scan по `idx_listings_brand_feed` | 237 мс | 162 мс, Bitmap Heap Scan |
| марка + год + цена | 132 мс | 1,1 мс, тот же индекс, год и цена фильтром | 130 мс | 166 мс |
| город + кузов | 129 мс | 11 мс, `idx_listings_feed` с фильтром | 123 мс | 138 мс, Seq Scan |
| страница 5000 (`offset 100000`) | 531 мс | 298 мс, `idx_listings_feed` | — | — |

Что видно:
- Страница теперь читается из индекса в нужном порядке и останавливается на 20-й строке: сортировки нет.
  Город с кузовом отдельного индекса не получили: лента идёт по `idx_listings_feed` и отбрасывает
  неподходящие строки, пока не наберёт 20. Это 11 мс, отдельный индекс того не стоит.
- `count` почти не ускорился, а для «марка + год + цена» и «город + кузов» стал чуть медленнее: чтобы посчитать
  6 тысяч подходящих Toyota, всё равно нужно пройти все 75 тысяч. Индекс по выражению `upper(brand)`
  не даёт Index Only Scan: в индексе лежит результат функции, а не сама колонка.
  Теперь `count` — почти всё время ответа. Варианты: не считать total вовсе (`Slice`, keyset-лента),
  брать оценку из статистики (`pg_class.reltuples`) или считать до предела (`count` по `limit 1000`).
- `offset` всё ещё дорогой: индекс избавил от сортировки, но 100 000 строк всё равно читаются
  и выбрасываются. Это решает лента по курсору, ниже.
- Запись подорожала: сид с двумя новыми индексами вместо одного старого шёл 41 секунду против 36,
  таблица с индексами выросла с 238 до 296 МБ.

## Частичный индекс и параметры

Hibernate передаёт статус параметром (`status = ?`), а частичный индекс построен под `status = 'ACTIVE'`.
План, построенный без значения параметра (generic plan), не может доказать, что `? = 'ACTIVE'`,
и такой индекс не берёт:

```sql
PREPARE feed(varchar) AS select id from listings where status = $1
    order by published_at desc, id desc offset 0 rows fetch first 20 rows only;
SET plan_cache_mode = force_generic_plan;
EXPLAIN EXECUTE feed('ACTIVE');   -- Parallel Seq Scan → Sort
SET plan_cache_mode = auto;
-- после 10 выполнений
EXPLAIN EXECUTE feed('ACTIVE');   -- Index Only Scan using idx_listings_feed
```

В режиме по умолчанию (`auto`) Postgres сравнивает generic plan со средним планом под конкретные значения
и оставляет последний, потому что generic в сотни раз дороже. Если когда-нибудь включить
`force_generic_plan`, лента вернётся к Seq Scan. Тогда частичный индекс меняют на обычный
`(status, published_at desc, id desc)`: он работает с любым значением параметра, но больше по размеру
и включает черновики и архив.

## Индексы на живой базе

В V10 стоит `CREATE INDEX CONCURRENTLY`: обычный `CREATE INDEX` на всё время построения запрещает запись
в таблицу. В V11 — `DROP INDEX CONCURRENTLY`: обычный `DROP INDEX` берёт эксклюзивную блокировку, ждёт
конца всех открытых транзакций, и за ним в очередь встают все запросы к `listings`. `CONCURRENTLY` нельзя
выполнять в транзакции. Flyway распознаёт такие команды и запускает скрипт вне транзакции, поэтому
в этих миграциях нет других команд.

Если построение оборвалось, остаётся невалидный индекс (`pg_index.indisvalid = false`). V10 перед каждым
`CREATE` делает `DROP INDEX CONCURRENTLY IF EXISTS`, поэтому повторный запуск его пересоздаст. Если упала
сама миграция, Flyway отметит версию 10 неудачной и не даст приложению стартовать: нужен `flyway repair`
или удаление этой строки из `flyway_schema_history`.
Блокировку Flyway пришлось перевести на сессионную (`spring.flyway.postgresql.transactional-lock: false`):
с блокировкой в транзакции `CONCURRENTLY` ждёт конца этой транзакции и висит. Тест миграций
(`MigrationOnLegacyDataTest`) настраивает Flyway сам и поймал это зависание первым.

## Лента по курсору (`/api/listings/feed`)

Вместо `offset` курсор: время публикации и id последней отданной строки. Hibernate строит

```sql
where l1_0.status=? and l1_0.published_at<=? and (l1_0.published_at<? or l1_0.id<?)
order by l1_0.published_at desc,l1_0.id desc fetch first ? rows only
```

Условие `published_at <= ?` стоит отдельно, хотя логически его покрывает `OR`: так оно становится
`Index Cond` и задаёт точку старта в `idx_listings_feed`. Одним `OR` индекс не ограничить, и Postgres
читал бы ленту с самого начала. Строк берётся на одну больше размера страницы: так видно, есть ли продолжение,
без `count`.

| Запрос | Время | План |
|---|---|---|
| `offset 100000`, страница 5000 | 299 мс | Index Scan, 100 020 строк прочитано и 100 000 выброшено |
| курсор на той же позиции | 0,15 мс | Index Scan с `Index Cond: published_at <= …`, 25 буферов |

Позиция курсора для замера берётся в `queries.sql` через `\gset` и в замер не входит.

## Поиск по словам (V12, V13)

`seed_text.sql` заменяет описания: в каждом три фразы из двадцати («Небольшой пробег», «Торг у капота»,
«Зимняя резина в подарок»…), каждая встречается примерно в 15% объявлений. «Панорамная крыша» — редкая,
у 0,2%. Среди опубликованных «небольшой пробег» у 105 146, «панорамная крыша» у 1 373.

Миграции мерил на миллионе строк: база на V11, сид и описания залиты, потом приложение накатило V12 и V13.

| Что | Время или размер |
|---|---|
| V12: `ADD COLUMN search_vector … STORED` | 19,4 с. Таблица переписывается под ACCESS EXCLUSIVE, всё это время закрыта и для чтения |
| V13: GIN `CONCURRENTLY` | 4,0 с, запись не блокирует |
| таблица без индексов | 308 → 512 МБ |
| GIN `idx_listings_search` | 14 МБ |
| UPDATE описаний у миллиона строк (`seed_text.sql`) | 30,0 с без вектора и GIN, 55,5 с с ними |

Запросы — как их строит Hibernate для `?q=`: без `sort` по релевантности (`ts_rank`), с `sort` и в `/feed` по дате.
Для сравнения тот же поиск через `ILIKE '%…%'`, как искали бы подстроку без полнотекстового индекса.

| Запрос | Страница | count |
|---|---|---|
| «небольшой пробег», 105 тысяч совпадений, по релевантности | 406 мс, Bitmap Index Scan по GIN → Sort | 311 мс |
| то же через ILIKE, по дате | 0,92 мс, `idx_listings_feed` с фильтром | 860 мс, Parallel Seq Scan |
| «панорамная крыша», 1 373 совпадения, по релевантности | 5,9 мс, GIN → Sort | 3,8 мс |
| то же через ILIKE, по дате | 45 мс, `idx_listings_feed` с фильтром | 857 мс, Parallel Seq Scan |
| «небольшой пробег» по дате (`/feed?q=`) | 0,56 мс, `idx_listings_feed` с фильтром | — |
| «панорамная крыша» по дате | 5,7 мс, GIN → Sort | — |
| «небольшой пробег» + марка Toyota, по релевантности | 292 мс, `idx_listings_brand_feed` → фильтр → Sort | 276 мс |

Что видно:
- GIN выигрывает, когда совпадений мало: редкая фраза за 6 мс против 45 мс у ILIKE, `count` 4 мс против 857.
- Частая фраза по релевантности медленная. `ts_rank` нужен каждой из 105 тысяч найденных строк, а для этого
  каждую нужно прочитать из таблицы. Эти строки лежат на 53 тысячах страниц из 65 тысяч, то есть запрос читает
  почти всю таблицу. Сама сортировка дешёвая: top-N heapsort на 27 КБ. `count` медленный по той же причине:
  у GIN нет Index Only Scan, каждую строку надо проверить в таблице.
- По дате частая фраза быстрая и без GIN: лента идёт по `idx_listings_feed`, подходит каждая седьмая строка,
  20 набираются сразу. Для редкой фразы так пришлось бы пройти тысячи строк, и планировщик сам берёт GIN
  с сортировкой. ILIKE по дате для частой фразы тоже быстрый, но его `count` читает всю таблицу.
- Хранимый вектор занимает место: таблица выросла на 204 МБ, в полтора раза. Можно обойтись без колонки,
  GIN по выражению `to_tsvector(...)`. Тогда таблица не растёт, но `ts_rank` и перепроверка строк после GIN
  считают `to_tsvector` заново для каждой найденной строки.
- Запись дороже: UPDATE описаний у миллиона строк шёл 55,5 с против 30,0: вектор пересчитывается, GIN пополняется.

Частая фраза по релевантности — известное ограничение. Варианты: ранжировать не все совпадения, а последние N
по дате; для частых слов отдавать по дате; RUM-индекс (расширение, хранит позиции и умеет `ORDER BY` по рангу
прямо из индекса); вынести поиск в Elasticsearch или OpenSearch. Пока ничего из этого не сделано.

### План в тесте

`SearchPlanTest` проверяет, что запрос `?q=` берёт `idx_listings_search`. Две ловушки, на которые он наткнулся:
- Свежие строки GIN копит в pending list (`fastupdate`) и при каждом поиске читает его целиком. Планировщик
  это учитывает: с 5000 только что вставленных строк он выбирал Seq Scan. В тесте список сливается
  `gin_clean_pending_list`, в работе это делает autovacuum.
- `ANALYZE` пишет `reltuples` в `pg_class` мимо транзакции, откат теста его не возвращает. В общем классе
  с другими тестами планов он сломал соседний тест курсора, поэтому у `SearchPlanTest` свой контейнер.

## Подсказки марок и моделей (V14)

Справочник `car_models` V14 собирает из опубликованных объявлений: на миллионе строк 3,2 с, вышло 45 пар.
На 45 строках Postgres читает справочник целиком за 0,14 мс. GIN по триграммам нужен,
когда справочник вырастет. Для проверки в транзакции добавлено 50 тысяч случайных пар:

| Запрос `toyta`, 50 тысяч пар | Время |
|---|---|
| Bitmap Index Scan по `idx_car_models_trgm` | 0,05 мс |
| Seq Scan (bitmap scan выключен) | 131 мс |

Сразу после вставки планировщик выбирал Seq Scan и на 50 тысячах: новые строки лежали в pending list GIN.
После `gin_clean_pending_list` — индекс. Та же ловушка, что в `SearchPlanTest`.
