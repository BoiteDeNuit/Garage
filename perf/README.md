# Замеры ленты

Как быстро отвечает `GET /api/listings` на миллионе объявлений и что меняют индексы.

## Как повторить

1. Поднять приложение, как в разделе «Запуск» основного README (`docker compose up -d --build`).
   При старте Flyway прогонит миграции, сид пишет в уже готовую схему.
2. Залить миллион объявлений (около 40 секунд). Скрипт откажется работать, если в `listings` уже больше 1000 строк:
   ```bash
   docker exec -i databaseGarage psql -U garage -d garage < perf/seed.sql
   ```
3. Снять планы:
   ```bash
   docker exec -i databaseGarage psql -U garage -d garage < perf/queries.sql
   ```

В `queries.sql` запросы ровно в том виде, в каком их строит Hibernate (снято через `show-sql`),
только параметры подставлены литералами. На каждую страницу Spring Data делает два запроса:
саму страницу и `count` для `totalElements`, поэтому замерены оба.

## Данные

`seed.sql` детерминирован (`setseed`), поэтому замеры повторяются.

| Что | Сколько |
|---|---|
| объявлений | 1 000 000: ACTIVE 699 754, SOLD 99 607, ARCHIVED 100 192, DRAFT 100 447 |
| продавцов | 500 |
| марок, моделей, городов | 15, 45, 20. Марки неравномерные: Lada чаще всего, Toyota — 75 тысяч активных |
| размер таблицы с индексами | 238 МБ |

## Где мерил

Postgres 16.15 в Docker с настройками по умолчанию (`shared_buffers` 128 МБ, `work_mem` 4 МБ,
2 параллельных воркера), 4 ядра. Каждый запрос — 10 прогонов после одного прогревочного, в таблице медиана
`Execution Time` из `EXPLAIN (ANALYZE, BUFFERS)`.

## До индексов

Из индексов только первичный ключ, `idx_listings_seller` и `idx_listings_brand_upper` по `UPPER(brand)`.

| Запрос | Страница | План страницы | count | План count |
|---|---|---|---|---|
| лента без фильтров | 225 мс | Parallel Seq Scan → Sort | 107 мс | Parallel Seq Scan |
| марка | 138 мс | Bitmap Index Scan по `UPPER(brand)` → Sort | 237 мс | Bitmap Heap Scan |
| марка + год + цена | 132 мс | Bitmap Index Scan по `UPPER(brand)` → Sort | 130 мс | Bitmap Heap Scan |
| город + кузов | 129 мс | Parallel Seq Scan → Sort | 123 мс | Parallel Seq Scan |
| лента, страница 5000 (`offset 100000`) | 531 мс | Parallel Seq Scan → Sort | — | — |

Что видно:
- Лента читает всю таблицу и сортирует 700 тысяч опубликованных, чтобы отдать 20 строк.
  Индекса под `published_at desc, id desc` нет.
- Индекс по марке находит 75 тысяч Toyota, но их всё равно приходится читать из таблицы и сортировать.
- `count` на каждую страницу стоит столько же, сколько сама страница: это половина времени ответа.
- Глубокая страница самая медленная: `offset` не пропускает строки, а сортирует и выбрасывает первые 100 000.
